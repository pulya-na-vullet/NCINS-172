# Разбор «Примеры работы Юрия.docx» (задачи Jira)

Источник: скриншоты Jira NCINS / эпики NEUROBUS.  
Контекст: проект **НФС.Некредитное страхование**.

## Что видно в целом

Документ — подборка тикетов, где паттерн повторяется:

1. **Задачи закрываются Done при пустом/заглушечном Description** (`Инструкция ищется...`).
2. **Требования уходят в личку / Confluence-ссылку без AC в Jira**.
3. **Discovery-тикеты — копипаст чеклиста** («все встречи / все заявки / все аппрувы»), без DoD.
4. **Часть наполнения делает мидл (Гузеев), хотя reporter — Юрий**.
5. **Позже вылезают дефекты ТЗ** (валидация `contractNumber` GENERATED→USED) — NCINS-232/233.
6. К июню–июлю качество Confluence чуть лучше (`NCINS-140` / prepare-documents от 22.06), но Jira-дескрипшены всё ещё тонкие.

Это хорошо стыкуется с разбором PDF: формально артефакты «есть», по содержанию часто нельзя отдать разработке/тесту без устных уточнений.

## Паттерны косяков (для разговора PO ↔ СА)

### 1. Done при Description = «Инструкция ищется...»
**Примеры:** NCINS-4, 5, 6, 9, 10, 11.

**PO:**  
«Юра, тикет Done, в Description до сих пор „Инструкция ищется...“. Где итог: что подняли, какой namespace, какие роли, ссылка на MR/Confluence? Как новому человеку повторить?»

**Риск:** нет аудита, знания только в головах/личке.

### 2. Требования в личке вместо ТЗ
**Пример:** NCINS-9 (и связанные клоны).

**PO:**  
«В подборке прямо написано: всё передавалось в сообщениях без структурированного ТЗ. Почему US на метод API закрыт без полей/ошибок/примеров в Jira или прилинкованном Confluence DoR?»

### 3. ТЗ на список договоров 1.5/10
**Пример:** NCINS-28 + Confluence «Получение списка Страховых договоров».

**Уже зафиксировано в docx, что нужно минимум:**
- логика поиска/фильтрации;
- обязательность и типы полей;
- коды ошибок;
- пагинация;
- убрать реальные ПДн из примеров → `{placeholder}`.

**PO:**  
«Согласен с оценкой 1.5/10. Почему это ушло в разработку? Кто аппрувил DoR?»

### 4. Закрытие без артефакта
**Пример:** NCINS-25.

**PO:**  
«Задача закрыта, результатов в тикете нет. Где лежит артефакт? Если его нет — почему Done, а не Cancelled/Moved?»

### 5. SA заводит, мидл наполняет; тест учится у мидлов
**Примеры:** NCINS-41, NCINS-45.

**PO:**  
«Ты reporter по NCINS-41, но описание дописывал Гузеев, а тест говорит, что запуск процесса объясняли мидлы. Где твоя SA-постановка: переменные Camunda, негативы, инциденты? Страница `ump-main-ma-ncins-pa` в выгрузке почти пустая — как тогда Done по управляющему процессу?»

### 6. Discovery-копипаст
**Примеры:** NCINS-65, NCINS-66 (одинаковый чеклист).

**PO:**  
«Discovery SFA→SignOnline и discovery АС 2.0 отличаются одной строкой заголовка. Где гипотезы, список систем, вопросы к владельцам, expected output (ADR/схема/решения)?»

### 7. Дыры ТЗ → продовые/тестовые баги
**Примеры:** NCINS-232, NCINS-233 (после NCINS-112).

- можно создать ACCOUNT с выдуманным `contractNumber` не из GENERATED;
- после создания статус номера не становится USED.

**PO:**  
«Это не „баг разработки“, это пропуск инвариантов в ТЗ. Почему в спеке создания договора не было обязательного pre-check GENERATED и post-condition USED?»

### 8. Однострочные discovery без результата
**Пример:** NCINS-135 — «узнать как и где подписываются доки в НИБе», weeks in To Do.

**PO:**  
«Какой deliverable discovery? Через 2 недели тикет всё ещё To Do/unassigned. Либо сужаем и закрываем результатом, либо эскалируем блокер.»

## Связь с выводами по PDF

| Наблюдение в Jira | Зеркало в Confluence PDF |
|---|---|
| `Инструкция ищется...` | Пустые Vision/SIgnOnline/process pages |
| Требования в личке | «Требования» SFA на 1 экран без AC |
| Копипаст discovery | Копипаст 6× НТ Worker |
| Баги GENERATED/USED | Слабые/дырявые API-спеки, заглушки примеров |
| Ссылка на ump-main-ma | Страница процесса ~60 слов |
| Улучшение после 22.06 | Появляются нормальные Service Task / НТ finalisation / БП.270 |

**Вывод для PO:** проблема не только в «плохих PDF», а в **системной дисциплине аналитика**: тикеты и страницы часто имитируют работу (Done + ссылка + клон), не создавая воспроизводимую постановку.

## Что попросить от СА на ближайший спринт (Definition of Ready)

1. В Jira Description минимум: цель, scope/out-of-scope, AC, ссылка на Confluence, ошибки/границы.  
2. Запрет Done при тексте `Инструкция ищется...` / пустых сабтасках.  
3. Discovery = список вопросов + ответственный + дата + артефакт-результат (не чеклист «все аппрувы»).  
4. Инварианты данных (GENERATED/USED и т.п.) явно в API-спеке до разработки.  
5. Если наполняет мидл — в тикете фиксировать автора описания и что именно SA согласовал.
